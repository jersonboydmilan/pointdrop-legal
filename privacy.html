What this app is

PointDrop hands a single geographic destination from one phone to another. It has no accounts, no login, and no user profile of any kind.

What we collect, and why

A destination you choose to send. When you send a destination, its name, address, and coordinates are stored on our server for as long as the code is valid (5–60 minutes, your choice), then automatically deleted. We store only a cryptographic hash of the code itself — never the code your driver scans.

A random, temporary device identifier. Each time you open the app, it generates a random string used only to prevent one device from creating excessive codes in a short time. It is not stored on your device, is not linked to any personal identifier, and is discarded when the app closes.

A random installation identifier, for search. Every place search costs us money, so searches are limited per installation. The first time you search, the app generates a random string and keeps it in its own storage until you uninstall the app. It is not derived from your device, your accounts, or your advertising ID, and it is sent only with search requests. Our server keeps only a one-way hash of it next to a request count, and a scheduled purge deletes that count within about a day.

Your network (IP) address. Every server sees the address a request comes from. Ours uses it only to limit how many requests one address can make: search keeps a shortened hash of it, and code creation counts against the address itself. Both counts are deleted by the same purge within about a day, and the address is never used to work out where you are.

Your location, if you allow it. Used only to show nearby places on the map and to bias search results toward where you are. It is read from your device and passed through our server to our search provider (see "Third parties" below) as part of a search request; it is never stored or logged on our servers.

Places you search for, pin, or have sent before. Your list of them is kept only on your device, in local app storage, and never sent to us. (The text of a search passes through our server on its way to the search provider; it is not stored or logged there.) Capped at 8 recent entries, deduplicated, and cleared any time you choose to clear it — with a confirmation step, since this cannot be undone.

Anonymous usage counters. We record that a code was created, opened, or led to navigation — never who did it. These counters are deleted along with the destination they describe, on the same schedule.

What we do not collect

We do not collect your name, email, phone number, or any persistent identifier other than the random installation identifier described above. We do not use analytics SDKs, advertising identifiers, or third-party trackers. We do not build a history of where you have been — your search history lives only on your phone and only until you clear it.

Third parties

  • Search and maps. Place search is handled by Geoapify (built on OpenStreetMap data) or Google Places API, whichever the operator has configured, reached through our server so that the app itself holds no search credentials — or by your device's own location services when our server is not configured. Map tiles are drawn from OpenStreetMap. Your search text and, when you grant permission, your approximate location, are passed to whichever provider is active; our server does not store or log them. Their own privacy policies govern that data.
  • Google Maps, at hand-off. Where no receiver page is deployed, the code itself is a Google Maps link, and scanning it hands the destination to Google under their privacy policy. This is the same as pasting the link into a message, and happens on the driver's phone, not ours.
  • Hosting. The backend runs on Supabase; the receiver page (what a driver sees when they scan a code) runs on whatever host the operator has deployed it to.

What a driver sees

When the operator has deployed the receiver page. The page a driver opens has no app, no account, and no cookies. It reads the destination tied to the code they scanned, shows it, and offers to open it in their own maps app. It records, anonymously, that the page was opened and that navigation was launched — nothing that identifies the driver.

When no receiver page is deployed — the configuration this app ships with today — the code is a direct Google Maps link built from the destination's coordinates. Scanning it opens Google Maps, and from that moment Google's own privacy policy governs what happens; we see nothing, so no "opened" or "navigated" signal is ever recorded.

Your controls

  • Delete your local history any time, from the app's home screen.
  • Revoke a code you have already sent, at any time before it expires, from the send screen — *when the operator has deployed the receiver page*. Without one, the code your driver scans is an ordinary Google Maps link. It cannot expire and cannot be revoked, a photograph of the screen opens it just as well, and the app says so on the send screen rather than offering a cancel button that would not work.
  • Deny location access — the app still works; only map-centering and search-biasing are affected.

Data retention

Server-side data (a sent destination and its code) is deleted automatically shortly after the code expires — at most 61 minutes after creation, by a purge that runs every 15 minutes.

One thing does outlive that window: where no receiver page is deployed, the code is a Google Maps link that carries the coordinates inside it. Deleting our copy does not unmake a link someone already holds. Send one only to a driver you mean to send it to.
